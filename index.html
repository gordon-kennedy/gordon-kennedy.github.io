    Killer App for Semantic Web🔗

    Introduction🔗

    The semantic web is a coherent and promising vision for repairing the traditional web. In an age where various aspects of the traditional web have become intrusive and socio-economically subversive, and AI now threatens to accelerate this trend alarmingly, many socially minded technologists see the semantic web as a last hope. To realise the vision a progressive sequence of determined initiatives and enterprises including linked data, ths Solid project and Inrupt have inspired investment from many areas; sadly, however, the hope is fading : progress has been slow and despite a period of encouraging growth in interest around the turn of the decade, the investment of time and money have recently been declining. Some possible reasons for this are proposed.

    One reason is that the semantic web is subject to a network challenge somewhat like the chicken and egg dilemma : investment-in-infrastructure follows demand-from-customers, and demand-from-customers follows investment-in-infrastructure. To reach a critical mass it has been suggested that the semantic web needs a killer application.

    A second reason is impenetrability; the semantic web promises to make web data easier to understand by storing structural information along with data. The promise is often presented as making data easier to understand for computers, but in addition there are big benefits from making data easier to search and interpret by humans too. Ironically, however, the nascent infrastructure of the semantic web has earned itself a counter-productive reputation for being hard to understand.

    This document makes a case for tackling both of these reasons by targeting a different audience. Advocates for the semantic web appear to be making an assumption that the technology will grow in a similar way to the traditional web grew. This is unlikely because back in the 90s the software developers, who embraced and used the web standards to write the software which made the web grow, had very different expectations and no alternative. Back then open-source products were in their infancy. Developers were accustomed to paying for tools from a limited choice of providers whose role was relatively easy for non-specialists to understand. Today, by contrast, software specialists are accustomed to combining multiple open-source tools at no cost, whose variety is vast and complicated and whose role is increasingly impenetrable to non-specialists. The unhealthy divide between specialist and non-specialist has grown much wider and more unhealthy. The semantic web could be packaged in a way to change this and offer a vital route in for non-specialists who increasingly have no alternative.

    In making the case several separate technical concepts are discussed and then drawn together in the conclusion.     Mind, Display & Storage : Three Models for Three Mediums🔗

    All applications exist to serve users 1 through a user-interface. A UI is some kind of layout, structured in space and/or time 2, which we could call a display model and which supports communication with the user. During this communication the display model effectively interfaces with the user's mental model, and the user is also aware of a third model for storing the information between sessions. The user may or may not expect to have open access to the storage model and this document will focus on the former case.

    Focus on Open Storage Models🔗

    Storage may be described as "open" of the user expects to be able to see and understand the stored data directly, i.e. independently from the UI. The user's mental model will always be shaped by the UI display model(s), and if the storage model is open then it will likely be shaped by that too. There may be three-way commonality between the display, mental & storage models, or the display model(s) may operate in a higher layer to the storage model.

    example provider type open storage model display model
    text file editing characters on page characters on page
    writing on paper characters on page characters on page
    MS-Excel cells in worksheets cells in worksheets and/or MS display components
    MS-Access cells in tables SQL queries and/or MS display components
    open data files shared scheme for decoding text or bytes application UI based on the public scheme
    SQL queryable databases cells in tables SQL queries and/or application UI
    NoSQL queryable databases dictionary of {name, value} pairs ?? queries and/or application UI
    SPARQL queryable endpoint RDF SPARQL queries and/or application UI

    Storage may be described as "closed" if the user expects to access the information through a UI from a single provider (notwithstanding an increasing user expectation to be able to export data from one provider's UI into another). The app provider has exclusive access to the storage and the user's mental model is shaped by the display model(s) only. Mental models held by developers within the app provider organisation, however, may still be shaped by the storage model.

    example provider type storage model display model
    MS-Word private to MS-apps document pages
    MS-Powerpoint private to MS-apps presentation slides
    SAP private to SAP custom business application UI
    web app private to web app app rendered in browser

    Since this document is aimed at exploring mental intelligibility closed storage will be ignored. In most cases the app providers with closed storage will rely privately on component platforms from lower level open storage providers anyway.

    Explicit Structure Is Preferable to Implicit🔗

    Coders are faced with various structural choices which can seem opposing :

    • choice of language can be strongly or weakly typed
    • choice of database can be SQL/schema or NoSQL/schemaless
    • choice of state can be common or variable

    A pattern appears in this list of choices, with the items on the left favouring explicit structure that's enforced according to a common declaration somewhere central to the code, and the items on the right favouring structure that's not so rigidly enforced but nevertheless remains subject to implicit structure expressed in scattered snippets across the codebase. Although there are cases where implicit structure can work better, explicit structure is generally easier to work.
